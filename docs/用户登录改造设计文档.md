## 2. 设计目标与边界

本设计在不破坏现有 Web 后台登录的前提下，完成微信小程序登录、统一账号、员工绑定、默认入口识别与会话管理。本期暂不实现认证与绑定审计日志。

小程序使用同一 AppID：

- 普通用户默认进入患者端；
- 所有用户默认进入患者端；有效员工额外显示工作台快捷入口；
- 本期不提供通用入口切换，但保留协议扩展字段；
- 小程序分包、Tab 和页面路由前端代码管理，不复用 `sys_menu`；
- `sys_role` / `sys_menu` 本期不调整，仍只服务 Web 后台权限；
- `STAFF` 只表示可进入工作台，不代表已获得项目成员、患者数据或明文权限。

## 3. 现状分析

### 3.1 现有 Web 登录

Web 登录由 `agileboot-admin` 承载：

```text
POST /login
  -> LoginService
  -> AuthenticationManager
  -> UserDetailsServiceImpl
  -> SystemLoginUser
  -> TokenService
  -> login_tokens:{uuid}
```

现有 JWT 只保存 `login_user_key`，实际登录上下文保存在 Redis；`JwtAuthenticationTokenFilter` 根据 JWT 中的 UUID 加载 `SystemLoginUser`。现有 Web 角色、菜单和数据权限逻辑可保留。

### 3.2 现有 API 登录

`agileboot-api` 中的 `LoginController`、`JwtTokenService` 和 `JwtAuthenticationFilter` 是演示性占位实现，使用固定字符串 `user1`，未实现真实账号、微信认证、Redis 会话和退出。本期将替换该占位链路。

### 3.3 存量兼容点

- `sys_user.status=1` 表示正常，`2` 表示停用，`3` 表示冻结；
- `sys_user.role_id` 为单角色字段，不用于小程序身份判断；
- `AppLoginUser` 已存在但字段不足，需替换为明确的小程序登录上下文；
- 存量 Web JWT 没有版本、客户端类型和主体类型，过渡期必须能继续解析。

## 4. 总体架构

```text
Web 后台                         微信小程序
   |                                  |
agileboot-admin                    agileboot-api
   |                                  |
Web LoginService                 MiniappAuthService
   |                                  |---- WechatCode2SessionClient ---- 微信 API
   |                                  |
   +------------- AuthSessionService -+
                       |
                  Redis 会话
                       |
                  agileboot-domain
              /           |            \
         sys_user      iam_user    iam_wechat_identity
```

实施原则：

1. Web 链路保留密码、验证码、`SystemLoginUser` 和菜单加载逻辑；
2. 小程序登录放在 `agileboot-api`，账号和绑定业务放在 `agileboot-domain`；
3. 微信 HTTP 调用通过接口隔离，便于测试和替换；
4. Web 与小程序使用相同的会话元数据规则，但使用不同的 Token 密钥和 Redis 命名空间；
5. 工作台入口识别与后续业务权限分开。

## 5. 关键设计决策

| 主题 | 本设计基线 | 理由 |
|---|---|---|
| 员工绑定 | Web 后台手动绑定 | 由管理员核对员工与小程序账号，首期不落认证/绑定审计日志 |
| 绑定存储 | `sys_user` 增加 `iam_user_id` 和 `miniapp_workbench_enabled` | 本期为一对一关系，改造量最小 |
| 解绑 | 只允许 Web 管理端执行 | 避免自助解绑导致身份风险；后续可增加审批流 |
| 多 AppID | 配置模型支持多 AppID，首期可只配置一个 | 数据唯一键本身已按 `app_id + open_id` 设计 |
| 项目角色 | 进入工作台后通过独立接口加载 | 避免 Token 固化频繁变化的权限 |
| 小程序菜单 | 不建菜单表 | 页面由前端管理，后端业务接口最终鉴权 |
| 身份切换 | 本期关闭，协议预留 | 员工默认进入患者端，通过快捷按钮进入工作台 |

上述为可直接实施的推荐基线。若评审改为手机号或审批绑定，仅替换绑定凭证校验器，不改变账号、会话和默认入口模型。

## 6. 领域模型

### 6.1 实体关系

```text
iam_user 1 -------- N iam_wechat_identity
    |
    | 0..1
    |
    0..1 sys_user
```

- `iam_user`：小程序的统一登录主体；
- `iam_wechat_identity`：可验证的微信身份，由 `app_id + open_id` 唯一定位；
- `sys_user`：Web 后台用户，可选绑定一个 `iam_user`；

### 6.2 枚举

| 枚举 | 值 |
|---|---|
| `ClientType` | `WEB_ADMIN`, `WECHAT_MINIAPP` |
| `SubjectType` | `SYS_USER`, `IAM_USER` |
| `IamUserStatus` | `NORMAL(1)`, `DISABLED(2)`, `FROZEN(3)` |
| `IdentityType` | `MINIAPP_USER`, `STAFF` |
| `EntryType` | `PATIENT`, `WORKBENCH` |

枚举放在 `agileboot-common`，数据库保存稳定的数值或英文代码，接口返回英文代码。

## 7. 数据库设计

### 7.1 `iam_user`

```sql
CREATE TABLE iam_user (
    user_id          BIGINT AUTO_INCREMENT COMMENT '统一账号ID' PRIMARY KEY,
    nickname         VARCHAR(64)  DEFAULT '微信用户' NOT NULL COMMENT '昵称',
    avatar           VARCHAR(512) DEFAULT '' NOT NULL COMMENT '头像地址',
    phone_number     VARCHAR(32)  DEFAULT '' NOT NULL COMMENT '手机号',
    status           SMALLINT     DEFAULT 1  NOT NULL COMMENT '1正常 2停用 3冻结',
    last_login_ip    VARCHAR(128) DEFAULT '' NOT NULL COMMENT '最后登录IP',
    last_login_time  DATETIME                NULL COMMENT '最后登录时间',
    creator_id       BIGINT                  NULL,
    create_time      DATETIME                NOT NULL,
    updater_id       BIGINT                  NULL,
    update_time      DATETIME                NULL,
    deleted          TINYINT(1)   DEFAULT 0  NOT NULL COMMENT '逻辑删除',
    KEY idx_iam_user_status (status)
) COMMENT '统一账号表';
```

### 7.2 `iam_wechat_identity`

```sql
CREATE TABLE iam_wechat_identity (
    identity_id  BIGINT AUTO_INCREMENT COMMENT '微信身份ID' PRIMARY KEY,
    user_id      BIGINT       NOT NULL COMMENT '统一账号ID',
    app_id       VARCHAR(64)  NOT NULL COMMENT '微信AppID',
    open_id      VARCHAR(128) NOT NULL COMMENT '微信OpenID',
    union_id     VARCHAR(128) DEFAULT '' NOT NULL COMMENT '微信UnionID',
    creator_id   BIGINT       NULL,
    create_time  DATETIME     NOT NULL,
    updater_id   BIGINT       NULL,
    update_time  DATETIME     NULL,
    deleted      TINYINT(1)   DEFAULT 0 NOT NULL COMMENT '逻辑删除',
    UNIQUE KEY uk_iam_wechat_app_open (app_id, open_id),
    KEY idx_iam_wechat_user (user_id),
    KEY idx_iam_wechat_union (union_id)
) COMMENT '微信身份表';
```

`open_id` 和 `union_id` 属于敏感标识：不在对外 DTO 中返回，不写入普通日志。如需更高数据库防护等级，可在后续引入确定性加密列及查询摘要列。

### 7.3 `sys_user` 扩展

```sql
ALTER TABLE sys_user
    ADD COLUMN iam_user_id BIGINT NULL COMMENT '绑定的统一账号ID' AFTER user_id,
    ADD COLUMN miniapp_workbench_enabled TINYINT(1) DEFAULT 0 NOT NULL
        COMMENT '是否允许使用小程序工作台' AFTER iam_user_id,
    ADD UNIQUE KEY uk_sys_user_iam_user (iam_user_id),
    ADD KEY idx_sys_user_workbench (miniapp_workbench_enabled, status);
```

项目现有 SQL 未统一使用外键，本设计也不增加物理外键，由事务和唯一索引保证一致性。

### 7.4 认证与绑定审计（后续扩展）

本期不创建认证与绑定审计表，也不写入登录、退出、绑定、解绑或工作台开关审计事件。后续如有合规要求，可独立增加审计模块；普通应用日志仍不得输出 code、SessionKey、Token、OpenID 等敏感数据。

### 7.5 绑定码存储（后续扩展）

首期不使用绑定码。为后续二维码或一次性凭证预留以下 Redis 模型：

```text
Key:   auth:staff-bind:{SHA-256(code + serverPepper)}
Value: { sysUserId, createdBy, createdAt, expiresAt, attemptCount }
TTL:   默认 10 分钟，可配置
```

- 展示绑定码只在创建成功响应中出现一次；
- 默认最多失败 5 次，超限后立即作废；
- 同一 `sys_user` 重新生成时作废旧码；
- 绑定成功与消费绑定码不能依赖单一分布式事务，最终以数据库唯一约束为准；成功提交后删除 Redis 凭证。

## 8. 登录上下文与会话

### 8.1 统一会话元数据

```java
AuthSession {
    String sessionId;
    ClientType clientType;
    SubjectType subjectType;
    Long subjectId;
    long issuedAt;
    long expiresAt;
    long lastAccessAt;
    long identityVersion;
    BaseLoginUser principal;
}
```

小程序 Principal 使用 `MiniappLoginUser`：

```java
MiniappLoginUser extends BaseLoginUser {
    Long iamUserId;
    Integer accountStatus;
    Long sysUserId;
    boolean workbenchEnabled;
    Set<String> identities;
}
```

`MiniappLoginUser` 不加载 Web 的 `RoleInfo`、菜单或项目权限。

### 8.2 JWT V2

新签发 JWT 包含：

```json
{
  "ver": 2,
  "sid": "5ef...",
  "ct": "WECHAT_MINIAPP",
  "st": "IAM_USER",
  "sub": "10001",
  "iat": 1790150400,
  "exp": 1790157600
}
```

约束：

- `sid` 是随机会话 ID，不可推测；
- JWT 中不放置完整 Principal、OpenID、SessionKey 和权限列表；
- API 过滤器必须校验 `ct=WECHAT_MINIAPP` 且 `st=IAM_USER`；
- Admin 过滤器必须校验 `ct=WEB_ADMIN` 且 `st=SYS_USER`；
- Web 过渡期允许缺少 `ver/ct/st` 但包含 `login_user_key` 的旧 Token，并固定按 Web Token 处理；
- 小程序不接受旧 Token。

### 8.3 Redis Key

```text
auth:session:{clientType}:{sessionId}                 -> AuthSession
auth:subject-sessions:{clientType}:{subjectType}:{id} -> Set<sessionId>
auth:staff-bind:{digest}                              -> StaffBindCode
auth:staff-bind-user:{sysUserId}                      -> digest
```

主体会话索引用于账号停用、解绑和关闭工作台时定向失效会话。删除会话时同步从 Set 移除 `sessionId`，Set 的 TTL 不小于会话 TTL。

### 8.4 有效期基线

| 配置 | 建议默认值 |
|---|---:|
| 小程序 Access Token | 120 分钟 |
| 小程序会话 | 120 分钟 |
| Web 新会话 | 沿用现有 30 分钟滑动策略 |
| 后续绑定码 | 10 分钟 |

小程序 Token 过期后重新执行 `wx.login` 即可，本期不发放长期 Refresh Token，降低凭证泄露面。如需无感续期，小程序可在到期前重新获取一次性 code 调用同一登录接口。

## 9. 小程序登录详细流程

### 9.1 正常流程

```text
1. 小程序调用 wx.login 获得 code
2. POST /miniapp/auth/login { appKey, code }
3. 服务端根据 appKey 读取受信任的 appId/appSecret
4. 调用微信 jscode2session
5. 检查 errcode 与 openid，不信任客户端提供的 openid
6. 按 appId + openid 查找微信身份
7. 若不存在，在一个数据库事务内创建 iam_user 和 iam_wechat_identity
8. 校验 iam_user.status
9. 查询 sys_user.iam_user_id，实时计算工作台状态
10. 生成 MiniappLoginUser、AuthSession 和 JWT
11. 更新最后登录信息
12. 返回用户、身份和默认入口
```

微信远程调用在数据库事务之外执行，避免长事务。首次并发登录由 `(app_id, open_id)` 唯一索引托底：插入冲突的事务整体回滚，然后重新查询已创建的身份，不留孤立 `iam_user`。

### 9.2 入口计算

```java
workbenchEnabled = iamUser.status == NORMAL
    && sysUser != null
    && sysUser.deleted == false
    && sysUser.status == NORMAL
    && sysUser.miniappWorkbenchEnabled == true;
```

```text
workbenchEnabled = false
  identities       = [MINIAPP_USER]
  defaultEntry     = PATIENT
  availableEntries = [PATIENT]

workbenchEnabled = true
  identities       = [MINIAPP_USER, STAFF]
  defaultEntry     = PATIENT
  availableEntries = [PATIENT, WORKBENCH]
```

`switchEntryEnabled` 本期始终返回 `false`，表示暂不提供通用身份切换接口。员工登录后由前端依据 `workbenchEnabled` 或 `availableEntries` 在患者端展示“工作台”快捷按钮；该按钮仅跳转工作台分包，不改变登录主体。

### 9.3 账号异常

- `iam_user` 停用或冻结：拒绝登录；
- 绑定的 `sys_user` 停用、冻结、删除或关闭工作台：允许以普通用户登录，不返回 `STAFF`；
- 微信返回异常：不创建本地账号；
- 未知 `appKey`：在调用微信前拒绝。

## 10. 员工绑定与解绑

### 10.1 Web 后台手动绑定

首期由管理员在 Web 后台完成绑定，小程序仅负责先登录创建待绑定的 `iam_user`。

1. 后台按昵称、手机号或不完整标识查询未绑定的 `iam_user`；
2. 管理员选择目标 `sys_user` 和待绑定 `iam_user`，核对昵称、头像、首次登录时间等信息；
3. 请求服务端不接受前端传入的 OpenID，只接受 `iamUserId` 和 `sysUserId`；
4. 事务内校验两方账号状态、删除标志和现有绑定状态；
5. 按条件更新 `sys_user.iam_user_id`，由唯一索引保证并发情况下不会重复绑定；
6. 提交成功后撤销该 IAM 用户现有小程序会话。

后台列表中不返回 OpenID、SessionKey 或完整微信身份标识。如无法仅凭昵称和头像确认人员，应在业务上增加手机号或工号核对字段，而不应直接暴露 OpenID。

### 10.2 后续绑定码流程

Web 管理端对目标 `sys_user` 执行：

1. 校验操作人具有账号管理权限；
2. 校验目标用户正常、未删除、已启用工作台且未绑定；
3. 生成至少 128 bit 随机性的凭证，对人工输入可使用 8 位无混淆字符并配合严格限流；
4. Redis 只保存加 Pepper 的摘要；
5. 返回一次性明文和过期时间。

### 10.3 后续小程序提交绑定

1. 从 Spring Security 上下文取得 `iamUserId`，不接受客户端传入；
2. 校验 IP + 账号级限流和错误次数；
3. 查找绑定码摘要，校验 TTL；
4. 事务内校验统一账号和 `sys_user` 状态；
5. 条件更新 `sys_user`：`WHERE user_id=? AND iam_user_id IS NULL AND status=1 AND deleted=0`；
6. `uk_sys_user_iam_user` 防止同一统一账号并发绑定两个员工；
7. 提交后作废绑定码，重建当前会话的身份摘要；
8. 返回新的上下文，前端默认进入患者端；员工根据上下文显示工作台快捷按钮。

所有对外绑定失败统一返回明确错误码，详细敏感信息不得写入普通应用日志。

### 10.4 解绑和关闭工作台

- 解绑使 `sys_user.iam_user_id=NULL`；
- 关闭工作台只修改 `miniapp_workbench_enabled=false`；
- 两者均在事务提交后使相关 IAM 会话中的员工摘要失效；
- 为避免“会话还在但工作台身份已撤销”的误解，本期简化为撤销该 IAM 用户全部小程序会话，客户端重新微信登录后以普通用户进入患者端；
- 操作必须记录操作人和原因。

## 11. API 设计

所有响应继续使用项目 `ResponseDTO<T>`。下文只展示 `data` 部分。

### 11.1 微信登录

```http
POST /miniapp/auth/login
Content-Type: application/json

{
  "appKey": "patient-miniapp",
  "code": "wx.login 一次性 code"
}
```

```json
{
  "accessToken": "***",
  "tokenType": "Bearer",
  "expiresIn": 7200,
  "sessionId": "5ef...",
  "clientType": "WECHAT_MINIAPP",
  "user": {
    "userId": 10001,
    "nickname": "微信用户",
    "avatar": ""
  },
  "identities": ["MINIAPP_USER", "STAFF"],
  "workbenchEnabled": true,
  "defaultEntry": "PATIENT",
  "availableEntries": ["PATIENT", "WORKBENCH"],
  "switchEntryEnabled": false,
  "staff": {
    "sysUserId": 12,
    "displayName": "张三"
  },
  "extensions": {}
}
```

`appKey` 是服务端配置别名，不是由客户端自由指定 AppSecret 的能力。如首期只有一个 AppID，可将 `appKey` 设为可选并使用服务端默认值。

### 11.2 获取当前身份上下文

```http
GET /miniapp/auth/context
Authorization: Bearer {token}
```

服务端从数据库重新计算员工状态和入口，不直接返回会话中的旧值。响应与登录结果中从 `user` 到 `extensions` 的部分相同，不重新返回 Token。

### 11.3 绑定员工（后续小程序自助流程）

```http
POST /miniapp/auth/staff/bind
Authorization: Bearer {token}
Content-Type: application/json

{
  "bindingCode": "ABCD2345"
}
```

成功响应为更新后的身份上下文。接口使用请求 ID 做幂等记录；已绑定到同一 `sys_user` 的重试可返回当前成功上下文，其他冲突不覆盖。

### 11.4 退出

```http
POST /miniapp/auth/logout
Authorization: Bearer {token}
```

删除当前会话并返回成功。会话已不存在时仍返回成功，但 Token 签名无效时仍按非法 Token 处理。

### 11.5 Web 管理端绑定接口

```text
GET    /system/iam-users/unbound
       查询待绑定的小程序统一账号

POST   /system/users/{userId}/miniapp-binding
       手动绑定，请求体为 { "iamUserId": 10001 }，需新增权限码 system:user:miniappBind

DELETE /system/users/{userId}/miniapp-binding
       解绑，请求体必须包含 reason，需 system:user:miniappUnbind

PUT    /system/users/{userId}/miniapp-workbench
       开启/关闭工作台，需 system:user:miniappWorkbench
```

这些是 Web 按钮权限，可挂在现有用户管理菜单下；它们不是小程序菜单。

### 11.6 Web 现有接口

`POST /login`、`POST /logout`、`GET /getLoginUserInfo` 和 `GET /getRouters` 路径与现有响应保持兼容。Web 新会话内部增加 `clientType/subjectType/sessionId`，不强制现有前端使用新字段。

## 12. 微信客户端设计

### 12.1 配置

```yaml
miniapp:
  auth:
    token-secret: ${MINIAPP_TOKEN_SECRET}
    access-token-ttl-minutes: 120
    bind-code-ttl-minutes: 10
    bind-code-max-attempts: 5
    bind-code-pepper: ${MINIAPP_BIND_CODE_PEPPER}
    apps:
      patient-miniapp:
        app-id: ${WECHAT_MINIAPP_APP_ID}
        app-secret: ${WECHAT_MINIAPP_APP_SECRET}
    wechat:
      connect-timeout-ms: 3000
      read-timeout-ms: 5000
```

生产 AppSecret、Token Secret 和 Pepper 只通过环境变量或密钥管理服务注入，不提交到仓库。

### 12.2 微信网关接口

```java
public interface WechatCode2SessionClient {
    WechatSession exchange(String appId, String appSecret, String code);
}
```

请求微信：

```text
GET https://api.weixin.qq.com/sns/jscode2session
    ?appid={appId}
    &secret={appSecret}
    &js_code={code}
    &grant_type=authorization_code
```

客户端实现要求：

- 配置连接和读取超时；
- 只对连接失败或 5xx 执行最多 1 次短退避重试，不重试无效 code；
- 日志只记录 `requestId/appKey/errcode/duration`；
- `session_key` 仅作为当次结果对象的内存字段，本期不落库、不入缓存。

## 13. 安全过滤器与鉴权

### 13.1 API SecurityFilterChain

```text
permitAll:
  POST /miniapp/auth/login

authenticated:
  GET  /miniapp/auth/context
  POST /miniapp/auth/staff/bind

logout handler:
  POST /miniapp/auth/logout
```

移除当前对 `/common/**` 的粗粒度全放行，删除固定 `user1` 的占位逻辑。

### 13.2 每次请求校验

1. 从 `Authorization: Bearer` 读取 Token；
2. 校验签名、`exp`、`ct`、`st` 和 `sid`；
3. 从 Redis 加载会话，不存在即未登录；
4. 校验 JWT 与会话的主体和客户端完全一致；
5. 构建 `UsernamePasswordAuthenticationToken` 写入 SecurityContext；
6. 小程序业务 Controller 使用 `AuthenticationUtils.getMiniappLoginUser()` 获取主体。

工作台后续接口不能只使用前端传入的 `workbenchEnabled`，必须以 SecurityContext 和最新的项目权限数据为准。

## 14. 错误码设计

在现有集中式 `ErrorCode` 中新增，具体数值实施时须先扫描全库避免现有重复码：

| 错误名 | 对外含义 | HTTP 建议 |
|---|---|---:|
| `MINIAPP_CODE_INVALID` | 登录凭证无效，请重试 | 400 |
| `MINIAPP_PROVIDER_UNAVAILABLE` | 微信服务暂时不可用 | 503 |
| `MINIAPP_APP_NOT_CONFIGURED` | 小程序配置无效 | 400 |
| `IAM_ACCOUNT_DISABLED` | 账号不可用 | 403 |
| `IAM_ACCOUNT_FROZEN` | 账号已冻结 | 403 |
| `AUTH_SESSION_EXPIRED` | 登录已过期 | 401 |
| `AUTH_CLIENT_MISMATCH` | 凭证不适用于当前客户端 | 401 |
| `STAFF_BIND_INVALID` | 绑定凭证无效或无法完成绑定 | 400 |
| `STAFF_ALREADY_BOUND` | 已完成员工绑定 | 409 |
| `STAFF_WORKBENCH_DISABLED` | 员工工作台未启用 | 403 |

绑定接口对外返回稳定错误码，内部日志只保留必要的非敏感诊断信息。

## 15. 并发、事务与幂等

| 场景 | 保护方式 |
|---|---|
| 同一微信用户首次并发登录 | 本地事务 + `uk_iam_wechat_app_open` + 冲突后重查 |
| 一个 IAM 用户并发绑定两个员工 | `uk_sys_user_iam_user` |
| 一个员工并发绑定两个 IAM 用户 | `UPDATE ... WHERE iam_user_id IS NULL` 并检查影响行数 |
| 同一绑定码重复提交 | Redis 原子消费标记 + 数据库幂等结果 |
| 重复退出 | 删除不存在会话仍返回成功 |
| 登录信息更新失败 | 不影响账号创建一致性；记录可观测错误 |

账号创建、身份创建和绑定必须使用 Spring `@Transactional`。事务提交后再更新/撤销 Redis 会话，避免数据库回滚但缓存已变更。

## 16. 日志与限流

### 16.1 请求 ID

- 优先接受网关传入的 `X-Request-Id`，不合法时服务端重新生成；
- 写入 MDC 和响应头；本期不写认证与绑定审计日志；
- 微信调用日志只用 request ID 关联，不输出 code/openid。

### 16.2 限流基线

| 接口 | 维度 | 建议值 |
|---|---|---:|
| 微信登录 | IP + appKey | 10 次/分钟 |
| 提交绑定码 | IAM 用户 + IP | 5 次/10 分钟 |
| 生成绑定码 | Web 操作人 + 目标用户 | 3 次/10 分钟 |

可复用项目 `@RateLimit`，但需扩展对小程序 Principal 和组合键的支持。

## 18. 迁移与发布

### 18.1 数据迁移

1. 创建 `iam_user`、`iam_wechat_identity`；
2. 向 `sys_user` 增加两个字段，存量账号 `iam_user_id=NULL`、`miniapp_workbench_enabled=0`；
3. 同步更新 MySQL 升级脚本及 H2/PG 测试 Schema；
4. 不迁移 `sys_user.user_type`、`role_id` 和存量密码。

### 18.2 发布顺序

```text
先执行兼容性 DDL
  -> 发布 agileboot-domain/infrastructure
  -> 发布 agileboot-admin（仍兼容旧 Token）
  -> 配置微信密钥
  -> 发布 agileboot-api
  -> 小程序灰度接入
```

回滚时先停止小程序入口，回滚应用。新表和可空字段保留，不在紧急回滚中删除数据。

### 18.3 Web Token 过渡

- 发布后新 Web 登录签发 V2 Token；
- 过渡期继续识别现有 `login_user_key` Token；
- 过渡窗口建议不超过现有 Redis 会话最长存活时间；
- 窗口结束后移除 V1 解析，并清理 `login_tokens:` 旧会话。

## 19. 测试设计

### 19.1 单元测试

- 入口判断的全组合：IAM 状态、绑定状态、`sys_user` 状态、工作台开关；
- 微信错误码到本地错误的映射；
- JWT 客户端/主体不匹配拒绝；
- 绑定码过期、错误次数、重复消费；
- 日志脱敏器不输出敏感值。

### 19.2 集成测试

- 首次登录创建且只创建一个账号；
- 同一 `appId + openId` 再次登录返回同一 `iamUserId`；
- 并发首次登录不生成孤立账号；
- 绑定成功后默认入口仍为 `PATIENT`，员工可通过患者端“工作台”按钮进入工作台；
- 解绑/停用后旧会话失效，重新登录进入 `PATIENT`；
- Web 存量用户登录、菜单和退出不受影响；
- Web Token 无法访问小程序受保护接口，反之亦然。

### 19.3 安全测试

- 伪造 OpenID、伪造签名、过期 Token、被撤销会话；
- 绑定码暴力猜测、用户枚举和重放；
- 请求/响应/异常日志的 code、Token、OpenID、SessionKey 泄露检查；
- 不同 `appKey` 之间的身份不能串用。

## 21. 待评审参数

以下内容已在文档中给出推荐基线，评审时可调整配置或策略：

1. 绑定码是否确定为首期绑定方式；
2. 生成绑定码的 Web 角色和权限码分配；
3. 绑定码是否使用 8 位人工输入字符，默认 10 分钟、5 次尝试；
4. 是否确定只允许 Web 管理员解绑；
5. 小程序 Access Token 默认 120 分钟是否合适；
6. 同一 IAM 账号允许的最大并发会话数，推荐首期 5 个；
7. 统一账号停用时是否立即踢出所有设备，推荐“是”；
8. 首期是否仅配置一个 AppID；
9. Web V1 Token 兼容窗口时长；
10. `iam_wechat_identity.open_id/union_id` 是否需要在本期即启用列加密。
