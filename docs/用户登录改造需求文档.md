# 用户登录改造需求文档

## 1. 文档信息

| 项目 | 内容 |
|---|---|
| 文档名称 | 用户登录改造需求文档 |
| 文档版本 | V1.2 |
| 编制日期 | 2026-09-23 |
| 适用项目 | AgileBoot Back End、Web 后台及微信小程序 |
| 文档状态 | 待评审 |

## 2. 背景

系统后续存在以下使用入口：

| 用户 | 入口 |
|---|---|
| 患者/家属 | 微信小程序患者端 |
| 项目员工（CRC 等） | 同一微信小程序内的员工工作台 |
| 项目负责人 | 微信小程序员工工作台、Web 后台 |
| 管理员 | Web 后台 |

患者端和员工工作台使用同一个微信小程序、同一个 AppID，并通过分包组织页面。当前阶段不实现完整业务权限体系，仅完成登录相关改造，使系统能够识别“当前是谁、从哪个入口登录、是否绑定员工身份、登录后默认进入哪里”。

小程序分包不是安全边界。后续业务接口仍须根据患者关系、项目成员关系和具体权限单独鉴权，本期登录改造不能代替后续权限改造。

## 3. 本期目标

1. 保持现有 Web 后台用户名密码登录可用；
2. 新增微信小程序登录能力；
3. 以 `AppID + OpenID` 唯一识别微信身份；
4. 建立微信身份与统一账号之间的关系；
5. 支持同一个小程序账号绑定现有后台员工账号；
6. 登录时识别普通小程序用户和员工身份，并确定登录后的默认入口；
7. 普通用户和员工登录后均默认进入患者端，员工额外显示进入工作台的快捷按钮；
8. 本期不提供通用身份切换入口，但在登录协议中保留后续切换扩展能力；
9. 统一不同入口的登录主体、Token、会话缓存和退出机制；
10. 为后续项目角色和业务权限改造预留扩展能力。

## 4. 范围说明

### 4.1 本期包含

- 现有 Web 后台登录兼容；
- 微信小程序 `wx.login` 登录；
- 统一账号创建和状态管理；
- 微信 OpenID 身份绑定；
- 小程序账号与现有 `sys_user` 员工账号绑定；
- 登录身份识别和工作台入口判断；
- Token 签发、解析、刷新、退出及会话失效；
- 登录和绑定相关的基础安全控制；
- 普通应用日志脱敏要求（本期不实现认证与绑定审计日志）；
- 与现有用户缓存和 Spring Security 登录上下文的兼容改造。

### 4.2 本期不包含

- 患者填表、上传材料、知情确认和状态查询；
- 患者本人或家属关系管理；
- 项目、人员和项目成员管理；
- 代录、补录、审核和驳回；
- 项目级角色授权；
- 患者数据脱敏规则；
- 明文查看、明文导出及二次确认；
- 业务数据访问审计；
- 管理员脱敏导出和完整审计日志查询；
- 小程序具体业务页面开发。

上述功能后续单独形成业务权限需求。本期仅在登录结果中预留身份和权限扩展字段。

## 5. 名词定义

| 名词 | 定义 |
|---|---|
| 统一账号 | 小程序登录主体，用于关联微信身份及可选的后台员工账号 |
| 微信身份 | 由 `AppID + OpenID` 唯一标识的登录身份 |
| 后台员工账号 | 现有 `sys_user` 中允许使用员工工作台的账号 |
| 普通小程序用户 | 已完成微信登录，但未绑定有效员工账号的用户 |
| 员工身份 | 统一账号已绑定有效且允许登录小程序工作台的 `sys_user` |
| 客户端类型 | 标识登录来源，如 `WEB_ADMIN`、`WECHAT_MINIAPP` |
| 登录主体 | 服务端完成认证后用于签发 Token 和建立安全上下文的账号 |
| 会话 | Token 对应的服务端登录状态及缓存数据 |

## 6. 登录主体模型

### 6.1 设计原则

- Web 后台继续以现有 `sys_user` 为认证主体；
- 微信小程序以统一账号为认证主体；
- 一个统一账号只能绑定一个有效微信身份在同一 AppID 下登录；
- 一个统一账号最多绑定一个现有 `sys_user` 员工账号；
- 一个 `sys_user` 最多绑定一个统一账号；
- 是否允许进入员工工作台与后台管理员身份分离，避免所有后台账号自动获得小程序工作台入口；
- 登录身份与业务权限分离，Token 不固化完整项目权限。

### 6.2 身份判断

小程序登录后的身份判断规则：

| 条件 | 身份结果 | 本期默认入口 | 本期切换能力 |
|---|---|---|---|
| 统一账号正常，未绑定员工 | `MINIAPP_USER` | 患者端 | 不提供切换 |
| 已绑定员工，但员工停用 | `MINIAPP_USER` | 患者端 | 不提供切换 |
| 已绑定正常员工，但未启用工作台 | `MINIAPP_USER` | 患者端 | 不提供切换 |
| 已绑定正常员工，且启用工作台 | `MINIAPP_USER`、`STAFF` | 患者端（显示工作台按钮） | 不提供切换 |
| 统一账号停用或冻结 | 不允许登录 | 无 | 无 |

说明：本期的 `MINIAPP_USER` 仅代表能够登录小程序，不代表已经获得某位患者的数据访问权。患者关系将在后续业务权限需求中实现。

## 7. 功能需求

### 7.1 Web 后台登录

#### 7.1.1 兼容要求

- 保留现有用户名、密码及验证码登录方式；
- 保留现有密码加密传输和 BCrypt 密码校验逻辑；
- 保留现有菜单权限、角色、部门和数据权限加载逻辑；
- 现有未绑定统一账号的后台用户仍可正常登录；
- 原有前端在过渡期内不应因 Token 字段扩展而无法使用。

#### 7.1.2 登录结果扩展

Web 登录生成的登录上下文应明确包含：

```text
clientType = WEB_ADMIN
subjectType = SYS_USER
subjectId = sys_user.user_id
sessionId
```

若当前 `sys_user` 已关联统一账号，可同时返回 `iamUserId`，但不得要求所有存量账号在本期完成绑定。

### 7.2 微信小程序登录

#### 7.2.1 登录流程

```text
小程序调用 wx.login
  → 获得临时 code
  → 调用后端微信登录接口
  → 后端调用微信 code2Session
  → 获得 OpenID、SessionKey，以及可选 UnionID
  → 按 AppID + OpenID 查询微信身份
  → 创建或加载统一账号
  → 检查统一账号状态
  → 查询是否绑定有效员工账号
  → 创建服务端会话并签发 Token
  → 返回身份及入口信息
```

#### 7.2.2 首次登录

- 当 `AppID + OpenID` 不存在时，创建统一账号和微信身份；
- 统一账号初始状态为正常；
- 首次登录不自动创建 `sys_user`；
- 首次登录不自动授予员工身份；
- 昵称、头像等资料由用户授权后更新，不作为登录唯一凭证；
- 如果账号创建过程任一步骤失败，整个创建过程应回滚，避免产生孤立身份。

#### 7.2.3 再次登录

- 根据 `AppID + OpenID` 定位统一账号；
- 检查账号是否正常；
- 重新计算员工绑定状态和默认入口，不直接信任上次登录结果；
- 更新最后登录时间、登录 IP 和必要的客户端信息；
- 同一 code 不得被重复使用。

#### 7.2.4 微信异常处理

- code 无效、已使用或过期时返回可识别的登录失败信息；
- 微信服务不可用时不创建临时本地账号；
- AppID 不匹配时拒绝登录；
- 日志中不得输出完整 code、SessionKey、OpenID 或 Token；
- SessionKey 原则上不长期保存，如后续手机号解密等能力需要使用，应加密、限制用途并设置有效期。

### 7.3 员工身份绑定

#### 7.3.1 绑定目标

员工绑定用于将小程序统一账号关联到现有 `sys_user`，从而在登录时识别员工身份并显示工作台入口。本期不在绑定过程中授予项目角色或业务数据权限。

#### 7.3.2 绑定规则

- 只能绑定状态正常的 `sys_user`；
- `sys_user` 必须被明确标记为允许使用小程序工作台；
- 一个 `sys_user` 只能绑定一个统一账号；
- 一个统一账号只能绑定一个 `sys_user`；
- 已绑定关系不能被普通用户直接覆盖；
- 绑定、解绑和换绑均需记录操作人、时间、结果及必要原因；
- 解绑后立即撤销员工身份，刷新身份后默认进入患者端，但不影响普通小程序登录。

#### 7.3.3 绑定方式

首期采用 Web 后台手动绑定：

1. 微信用户先通过小程序登录，创建未绑定的统一账号；
2. 管理员在 Web 后台查找待绑定的统一账号，选择目标 `sys_user`；
3. 后台核对员工身份和小程序账号信息后提交绑定；
4. 服务端在事务内校验双方均未绑定其他账号，建立一对一关系；
5. 绑定成功后使相关小程序会话失效，用户重新登录后默认进入患者端；员工可在患者端通过“工作台”按钮进入工作台。

后续可增加绑定码或二维码确认流程，但不改变绑定关系和唯一约束。

### 7.4 默认入口识别

登录服务负责判断登录后的默认入口，不负责计算完整项目权限。

`workbenchEnabled=true` 必须同时满足：

```text
统一账号状态正常
+ 已绑定 sys_user
+ sys_user 状态正常
+ sys_user 允许使用小程序工作台
```

默认入口规则：

```text
workbenchEnabled = true  → defaultEntry = PATIENT，显示“工作台”入口按钮
workbenchEnabled = false → defaultEntry = PATIENT，不显示“工作台”入口按钮
```

小程序收到登录结果后直接进入 `defaultEntry` 对应页面，并按需加载相应分包。员工登录后仍停留在患者端，界面根据 `workbenchEnabled` 或 `availableEntries` 展示“工作台”按钮，点击后跳转员工工作台；普通用户不展示该按钮。该按钮是入口跳转，不代表开放通用身份切换。后续每个业务接口仍必须独立校验项目成员和业务权限。

为方便后续支持身份切换，登录协议保留 `availableEntries` 和 `switchEntryEnabled` 字段：

- 本期 `switchEntryEnabled` 固定为 `false`；
- 本期前端使用 `defaultEntry` 进入患者端；员工根据能力字段展示工作台快捷按钮，不展示入口选择页面；
- 后续开放切换时，由服务端根据有效身份计算 `availableEntries`，无需改变 Token 主体；
- 预留字段不能作为后端业务授权依据。

项目负责人身份、项目列表和项目内角色不在本期登录接口中强制实现。登录结果预留 `extensions` 或版本化身份字段，后续可通过独立接口加载项目上下文。

### 7.5 登录结果

小程序登录结果建议如下：

```json
{
  "accessToken": "***",
  "expiresIn": 7200,
  "sessionId": "***",
  "user": {
    "userId": 10001,
    "nickname": "微信用户",
    "avatar": "https://..."
  },
  "clientType": "WECHAT_MINIAPP",
  "identities": ["MINIAPP_USER", "STAFF"],
  "workbenchEnabled": true,
  "defaultEntry": "PATIENT",
  "availableEntries": ["PATIENT", "WORKBENCH"],
  "switchEntryEnabled": false,
  "staff": {
    "sysUserId": 12,
    "displayName": "张三"
  }
}
```

约束：

- 未绑定员工时，`identities` 不包含 `STAFF`，`staff` 为空；
- 未绑定有效员工时，`defaultEntry=PATIENT` 且不展示工作台按钮；绑定有效员工时，`defaultEntry` 仍为 `PATIENT`，同时展示工作台按钮；
- 本期无论用户具备几个潜在入口，`switchEntryEnabled` 均为 `false`；
- 登录结果不返回 OpenID、SessionKey、密码哈希等认证敏感信息；
- 登录结果不返回完整项目权限；
- 前端不能提交或修改 `identities`、`workbenchEnabled` 作为服务端授权依据。

### 7.6 Token 与会话

#### 7.6.1 Token 内容

Token 至少能够关联以下信息：

```text
sessionId
clientType
subjectType
subjectId
issuedAt
expiresAt
```

建议：

- Web：`clientType=WEB_ADMIN`、`subjectType=SYS_USER`；
- 小程序：`clientType=WECHAT_MINIAPP`、`subjectType=IAM_USER`；
- Token 中不放置 OpenID、SessionKey、完整权限集合和患者敏感信息；
- 不同主体类型的 ID 即使数值相同，也不能共用会话缓存键。

#### 7.6.2 会话缓存

会话缓存键至少包含客户端类型、主体类型或全局唯一 Session ID，防止 Web 用户 ID 与小程序用户 ID 冲突。

缓存的登录上下文至少包含：

- 统一登录主体；
- 客户端类型；
- 账号状态；
- 员工绑定摘要；
- 创建时间、最后访问时间和过期时间；
- 权限或身份版本号预留字段。

#### 7.6.3 刷新与失效

- 支持在会话接近过期时按现有策略续期或刷新；
- 用户主动退出后，服务端会话立即失效；
- 统一账号停用或冻结后，其全部小程序会话失效；
- `sys_user` 停用、关闭工作台或解除绑定后，员工身份相关缓存立即失效；
- 员工解除绑定不必强制注销普通小程序身份，但后续请求不得再获得工作台身份；
- 修改 Web 后台密码后，是否踢出全部 Web 会话沿用现有安全策略或另行确认。

### 7.7 退出登录

- Web 和小程序分别提供退出入口；
- 退出只注销当前会话，不默认删除统一账号或微信绑定；
- 服务端删除或标记对应会话失效；
- 重复退出应返回成功，不产生异常；
- 退出后使用原 Token 访问受保护接口必须失败。

## 8. 数据模型需求

### 8.1 统一账号表

建议新增 `iam_user`：

```text
user_id
nickname
avatar
phone_number
status                 NORMAL / DISABLED / FROZEN
last_login_ip
last_login_time
created_time
updated_time
deleted
```

说明：手机号不是微信身份的唯一键，不能仅凭微信提供或用户填写的手机号自动合并账号。

### 8.2 微信身份表

建议新增 `iam_wechat_identity`：

```text
identity_id
user_id
app_id
open_id
union_id
created_time
updated_time
```

约束和索引：

```text
UNIQUE (app_id, open_id)
INDEX (user_id)
INDEX (union_id)
```

### 8.3 员工绑定

建议在 `sys_user` 增加：

```text
iam_user_id                 可空，唯一
miniapp_workbench_enabled   默认 false
```

约束：

- `iam_user_id` 唯一，防止一个员工账号绑定多个小程序账号；
- 历史后台账号的 `iam_user_id` 保持为空，不影响 Web 登录；
- 管理员账号不因 `is_admin=true` 自动启用小程序工作台；
- 是否启用工作台使用明确字段或等价的登录入口授权配置。

如不希望修改 `sys_user`，也可以使用独立绑定表，但必须具备双方唯一约束和绑定状态字段。

### 8.4 绑定码（后续扩展）

一次性绑定码可存储于 Redis 或数据库，至少包含：

```text
code_digest
sys_user_id
expires_at
used_at
created_by
attempt_count
```

禁止明文长期保存绑定码。

## 9. 接口需求

建议接口边界：

```text
POST /miniapp/auth/login
    使用微信 code 登录

GET /miniapp/auth/context
    刷新当前身份及入口信息

POST /miniapp/auth/staff/bind
    使用受控凭证绑定员工账号

POST /miniapp/auth/logout
    注销当前小程序会话

POST /admin/auth/login
    保持现有 Web 登录能力

POST /admin/auth/logout
    注销当前 Web 会话
```

接口要求：

- 登录和绑定接口需要限流；
- 请求日志对 code、Token、绑定码等字段脱敏；
- 绑定接口需要防重复提交；
- 所有错误使用项目现有 `ResponseDTO`、`ApiException` 和集中式错误码；
- 对外错误信息不得泄露某个 `sys_user` 是否存在、是否已绑定等可被枚举的信息。

## 10. 错误场景

至少覆盖以下错误：

| 场景 | 处理要求 |
|---|---|
| 微信 code 无效或过期 | 返回重新登录提示，不创建账号 |
| 微信接口不可用 | 返回可重试错误，不降级为匿名登录 |
| 统一账号停用 | 拒绝登录 |
| 统一账号冻结 | 拒绝登录并返回统一状态码 |
| 员工账号停用 | 普通小程序登录可继续，工作台身份不可用 |
| 员工未启用工作台 | 普通小程序登录可继续，不显示工作台 |
| 绑定码无效或过期 | 绑定失败，不暴露员工信息 |
| 员工已经绑定其他账号 | 绑定失败，进入受控换绑流程 |
| 当前账号已经绑定其他员工 | 绑定失败，不覆盖原绑定 |
| Token 过期或会话不存在 | 返回未登录状态 |
| 客户端类型不匹配 | 拒绝访问对应入口接口 |

## 11. 安全与日志边界

### 11.1 本期审计范围

本期不创建认证与绑定审计日志表，也不记录登录、退出、绑定、解绑、工作台开关等审计事件。后续如有合规或运营需要，单独提出审计模块需求。普通应用日志不得记录密码、Token、微信 code、SessionKey、完整 OpenID 或完整绑定码。

### 11.2 安全要求

- 登录、验证码和绑定接口需要限流和防暴力尝试；
- 服务端必须校验请求使用的是已配置 AppID；
- 仅从微信服务端返回结果中信任 OpenID，不接受前端直接传入 OpenID 完成登录；
- Token 必须具有有效期并支持服务端撤销；
- Web Token 和小程序 Token 不能互相访问只允许特定客户端的接口；
- 账号和绑定状态变化后应主动清理或刷新相关缓存；
- 所有认证通信必须使用 HTTPS；
- 配置文件不得提交微信 AppSecret、生产密钥或真实 Token。

## 12. 非功能要求

- 登录接口应保证账号和微信身份创建的事务一致性；
- 重复提交同一个有效登录请求不得生成多个微信身份；
- `AppID + OpenID` 唯一约束作为并发登录的最终保护；
- 身份上下文接口应满足小程序首屏初始化需要，避免多次串行请求；
- 微信服务调用应配置合理的连接和读取超时；
- 登录链路需具备请求 ID，便于排查微信调用、账号创建和 Token 签发问题；
- 新增缓存键应与现有用户缓存隔离，避免不同登录主体相互覆盖。

## 13. 兼容与迁移要求

1. 新增表和字段不得影响现有 `sys_user` 数据；
2. 存量 Web 后台账号无需统一迁移即可继续登录；
3. 需要使用小程序工作台的员工按需完成绑定；
4. Web 登录 Token 改造如涉及格式变化，应支持灰度或明确要求存量会话重新登录；
5. 原有 Redis 登录缓存升级时应使用新命名空间，避免覆盖生产中的旧缓存；
6. 不使用现有 `sys_user.user_type` 表示客户端入口；
7. 不使用现有单值 `sys_user.role_id` 判断患者身份或完整项目角色。

## 14. 验收标准

### 14.1 Web 登录

- [ ] 未绑定统一账号的存量后台用户仍能正常登录、退出和访问原有功能。
- [ ] Web 登录上下文能够识别 `WEB_ADMIN` 和 `SYS_USER`。
- [ ] 原有密码、验证码、角色和菜单权限逻辑未被破坏。

### 14.2 小程序登录

- [ ] 首次微信登录只创建一个统一账号和一条微信身份记录。
- [ ] 重复或并发登录不会产生重复的 `AppID + OpenID`。
- [ ] 再次登录能够定位同一统一账号。
- [ ] 前端直接伪造 OpenID 不能完成登录。
- [ ] 账号停用或冻结后无法登录。
- [ ] 登录结果不包含 OpenID、SessionKey、密码或完整权限集合。

### 14.3 员工绑定与默认入口

- [ ] 普通小程序用户登录后默认进入患者端。
- [ ] 绑定有效且已启用工作台的员工登录后默认进入患者端，并显示“工作台”按钮。
- [ ] 普通用户不显示“工作台”按钮。
- [ ] 本期不展示患者端与员工工作台的通用身份切换入口。
- [ ] 登录结果包含 `defaultEntry`、`availableEntries` 和 `switchEntryEnabled=false`，为后续切换预留协议扩展。
- [ ] 员工停用或关闭工作台后，再次刷新身份默认进入患者端。
- [ ] 一个员工账号不能同时绑定两个小程序账号。
- [ ] 一个小程序账号不能同时绑定两个员工账号。
- [ ] 解绑员工后普通小程序登录仍然有效，员工身份立即失效。
- [ ] 管理员账号不会仅因 `is_admin=true` 自动获得工作台入口。

### 14.4 Token 与会话

- [ ] Web 和小程序 Token 能区分客户端类型和主体类型。
- [ ] 数值相同的 `sys_user.user_id` 与 `iam_user.user_id` 不会共享会话缓存。
- [ ] 主动退出后原 Token 不能继续访问受保护接口。
- [ ] 统一账号停用后已有小程序会话失效。
- [ ] Web Token 不能调用仅允许小程序的接口，反之亦然。

### 14.5 安全与日志

- [ ] 登录和绑定接口具备限流控制。
- [ ] 日志中不出现密码、Token、微信 code、SessionKey 和完整绑定码。
- [x] 本期不实现认证与绑定审计日志，普通日志保持脱敏。
- [ ] 绑定失败不会向调用方泄露可枚举的员工账号详情。

## 15. 后续迭代接口

本期完成后，后续需求将在统一账号和登录上下文之上继续实现：

- 患者本人/家属关系；
- 项目员工和项目负责人角色；
- 项目成员数据范围；
- 代录、审核及驳回权限；
- 患者信息脱敏；
- 明文查看、明文导出和二次确认；
- 完整敏感数据访问审计。

后续权限判断不得仅依赖本期返回的 `STAFF` 身份或 `workbenchEnabled` 字段。

## 16. 待评审确认项

1. 首期已确定由 Web 后台管理员手动绑定；后续是否增加一次性绑定码或二维码流程；
2. 后台查询待绑定小程序账号时，采用哪些非敏标识进行人员核对；
3. 是否允许员工自助解绑，换绑是否必须由管理员审核；
4. `sys_user` 是否直接增加 `iam_user_id` 和 `miniapp_workbench_enabled` 字段，还是使用独立绑定表；
5. Web 与小程序 Token 的有效期、自动续期时间及并发会话数量；
6. 账号停用时是否踢出全部设备会话；
7. 是否需要同时兼容多个部署环境或多个 AppID；
8. Web Token 格式变化后，是否允许存量会话自然过期；
9. 项目角色信息是在登录响应中加载，还是进入工作台后通过独立接口加载；
10. 后续开放身份切换时，员工切换到患者端是否需要先具备有效患者关系。
